## 1. High-level workflow automated training pipeline

```
GitLab event / manual trigger     правила запуску — розд. 4
        ↓
GitLab CI pipeline                перевірка коду, збірка образу, Git-контекст
        ↓
AWS Step Functions execution      оркестратор MLOpsPipeline, у кожного кроку свій статус
        ↓
Data validation                   не пройдено → стоп і сповіщення, GPU не витрачено
        ↓
Training job                      timeout 6 год, збій ноди → один повтор
        ↓
Model evaluation                  порівняння з production-моделлю на еталонному наборі
        ↓
Logging metrics and artifacts     параметри, метрики, артефакти в MLflow
        ↓
Model Registry update             статус candidate або rejected, але не production
        ↓
Notification to team              за будь-якого результату, з owner-ом і наступною дією
```

| Питання | Відповідь |
|---|---|
| Що запускає pipeline? | Погоджені події: зміна model config або коду тренування в `main`, розклад, ручний запуск (розд. 4) |
| Яка роль GitLab CI? | Trigger і Git-контекст: перевіряє код, збирає образ, запускає execution і передає commit SHA, branch, `source="gitlab-ci"`, версію датасету |
| Яка роль AWS Step Functions? | Оркестратор типу Standard (Express обмежений 5 хв і не чекає завершення job): задає порядок кроків, перевіряє результат кожного, керує повторами, timeout-ами й обробкою помилок. Модель він не тренує: короткі перевірки виконує Lambda, навчання — Kubernetes Job у namespace `training` на GPU-нодах (ДЗ №2), який Step Functions запускає через інтеграцію з EKS |
| Де фіксуються метрики? | У MLflow: параметри, метрики, артефакти з посиланням на commit і execution. Для дашборда метрики паралельно йдуть у Prometheus, і сповіщення на них не чекає |
| Де зберігається модель-кандидат? | Артефакт — у S3, версія зі статусом — у Model Registry, із посиланням на MLflow run |
| Хто отримує повідомлення? | Slack-канал команди; відповідальний за наступний крок названий у самому повідомленні (розд. 7) |

**Логіка процесу нелінійна.** Після кожного кроку Step Functions перевіряє результат. Технічний збій (зникла GPU-нода, контейнер перестав відповідати) усувається одним повтором. Решта помилок одразу переходить до сповіщення: якщо навчання впало на 15-й хвилині багатогодинного запуску, owner має дізнатися про це одразу, а не наприкінці запланованого часу.

**Чому саме ця зв'язка.** Альтернативи — bash-скрипт у CI job або Apache Airflow чи Kubeflow Pipelines. Скрипт не потребує нового сервісу, але повтори, статуси й розгалуження доведеться писати й підтримувати самим. Airflow і Kubeflow не прив'язані до одного хмарного провайдера, але це ще один сервіс, який команда має підтримувати. Step Functions не потребує власних серверів і дає видимий у AWS Console статус кожного кроку. Недолік обраного — прив'язка до AWS: якщо він подорожчає, переїхати буде важче. Компенсація: опис workflow зберігається файлом у Git і розгортається через Terraform, а навчання запаковане в контейнер, тому його можна запустити під іншим оркестратором. Є й технічне обмеження: інтеграція Step Functions з EKS працює лише з публічним API-endpoint кластера, тому такий доступ до `eks-nonprod` звіряємо з вимогами безпеки ще до запуску; owner — MLOps Engineer.

## 2. Контрольні точки pipeline

| Етап pipeline | Що перевіряє команда | Хто owner | Що є успіхом | Що робити при помилці |
|---|---|---|---|---|
| GitLab CI trigger | Подія дозволена правилами, образ зібрано, Git-контекст передано | MLOps Engineer | Execution стартував, його назва є в логах job | Pipeline червоний, навчання не стартує; перевірити права ролі й правила запуску |
| Data validation | Версія датасету, схема, обов'язкові поля (файл, клас), частка битих файлів, обсяг | Data Engineer | Усі перевірки пройдено, версію датасету зафіксовано | Зупинити pipeline до навчання, повідомити owner-а |
| Training | Версія коду й даних, параметри, тип інстансу, тривалість | AI/ML Engineer | Job завершився в межах 6 год, артефакт створено | Збій ноди — один повтор; помилка коду — без повтору, owner розбирає логи CloudWatch; повторний збій — incident |
| Evaluation | Метрики на еталонному наборі, порівняння з production-моделлю, ключові категорії | AI/ML Engineer + AI PM | ML-метрики й порівняння з production-моделлю в межах порогів розд. 3 | Статус rejected, модель далі не просувається |
| Logging | Параметри, метрики, артефакти, commit SHA, версія даних у MLflow | MLOps Engineer | Run із повним контекстом видно в MLflow | Зупинити pipeline: модель без запису не реєструється; перевірити доступ до MLflow і S3 |
| Model Registry | Нова версія, статус, посилання на run | MLOps Engineer | Версія має статус candidate або rejected | Перевірити реєстр і логування; вручну статус candidate або rejected не виставляти |
| Notification | Команда отримала зрозумілий статус | AI PM + MLOps Engineer | Повідомлення з розд. 7 у каналі протягом 10 хв після завершення | Alert для MLOps Engineer, статус перевірити в AWS Console за runbook |

## 3. Quality gates для нової моделі

| Quality gate | Правило | Хто перевіряє | Рішення |
|---|---|---|---|
| Data quality | Немає критичних помилок схеми, битих файлів < 1 %, у кожному класі ≥ 200 фото | Автоматично; owner — Data Engineer | Продовжити або зупинити pipeline |
| ML-метрики | Macro-F1 ≥ 0,85 і top-1 accuracy ≥ 0,90 на еталонному наборі | Автоматично; owner — AI/ML Engineer | Продовжити або rejected |
| Порівняння з baseline | Macro-F1 не нижчий, ніж у поточної production-моделі, на тому самому наборі | Автоматично; owner — AI/ML Engineer | Продовжити або rejected |
| Відтворюваність | Є commit SHA, версія датасету, параметри й артефакт | Автоматично; owner — MLOps Engineer | Реєструвати або зупинити |
| Бізнес-критерій | Top-3 accuracy не нижча, ніж у production: менеджер бачить три варіанти (ДЗ №1). На ключових категоріях каталогу recall не падає більше ніж на 2 в. п. | AI PM | Погодити або rejected |
| Approval | Метрики підтверджує ML Lead, бізнес-критерій — AI PM (manual approval у Model Registry) | ML Lead + AI PM | Статус approved: дозволити staging |
| Перехід у production | Staging пройдено, rollback-план є, реліз іде через GitOps (ДЗ №3) | Tech Lead + ML Lead, вікно релізу — AI PM | Статус production або rejected |

Перші чотири gates перевіряє сам pipeline. Якщо не пройшли дані чи відтворюваність — зупинка без нової версії; якщо ML-метрики чи baseline — rejected; якщо пройшли всі чотири — candidate. Решту вирішують люди, уже після candidate, тому manual approval потрібен завжди. Шлях статусів: candidate → approved → staging → production; rejected — на будь-якому етапі до production. У MLflow такий статус — це тег або alias версії: фіксованих статусів і вбудованого approval у Model Registry немає, тому рішення людини фіксується тегом.

**Модель технічно навчилась, але не пройшла gates.** Вона отримує статус rejected із причиною, а її run лишається в MLflow для аудиту. Production-модель не змінюється. Команда отримує сповіщення, і AI/ML Engineer разом з AI PM протягом двох робочих днів вирішують: зібрати більше даних, змінити параметри чи закрити спробу. Обходу gates немає.

**Технічний success — не готовність до production.**

| | Технічний success pipeline | Production-readiness моделі |
|---|---|---|
| Питання | Чи відпрацювали всі кроки? | Чи можна довірити цю модель користувачам? |
| Докази | Зелений GitLab job, execution `Succeeded`, запис у MLflow, автоматичні gates відпрацювали | Бізнес-критерій, approval, перевірка в staging, rollback-план |
| Хто вирішує | Автоматика | ML Lead, AI PM, Tech Lead |
| Результат | Версія зі статусом candidate або rejected | Статус production після staging і погодження, реліз через GitOps |

## 4. Правила запуску training pipeline

| Trigger | Коли доречний | Перевага | Ризик | Середовище | Контроль |
|---|---|---|---|---|---|
| Push або merge у `main` | Навчальний сценарій, малий проєкт | Простий запуск | Навчання після кожного merge, навіть не про модель: зайві runs і витрати | dev | Лише без GPU або на малому наборі |
| Зміна model config або коду тренування | Постійна робота над моделлю | Запуск лише за релевантних змін | Неточні правила пропустять потрібну зміну або запустять зайве | dev, staging | Перелік шляхів у правилах затверджує MLOps Engineer |
| Manual trigger | Перевірка гіпотези, нова версія датасету | Людина контролює момент і ціну | Залежить від дисципліни; запуск без погодження витрачає бюджет | staging, prod | Запускає лише AI/ML Engineer; понад 5 запусків на місяць сумарно з усіх trigger-ів — погодження AI PM |
| Schedule | Плановий retraining, раз на місяць | Передбачуваність витрат | Тренує, навіть якщо дані не змінилися | staging, prod | Перед навчанням перевірити наявність нових даних; немає — пропустити запуск |
| Сигнал drift або деградації | Зрілий моніторинг якості | Запуск за реальною потребою | Хибний сигнал запускає дорогі runs | prod, на пізнішому етапі | Сигнал спершу перевіряє людина; не частіше ніж раз на тиждень |

Стовпець «Середовище» показує, для якого середовища готуємо модель; власне GPU-навчання завжди йде в namespace `training` (ДЗ №2). Жоден trigger не виводить модель у production: результат — лише нова версія в реєстрі, яка далі проходить approval.

**Вибір і ціна.** Оцінка: один запуск ≈4 год на `g5.xlarge`, уточнимо за тривалістю нинішніх ручних запусків. За ≈1,01 USD/год (on-demand, `us-east-1`) це ≈4 USD. Орієнтир із ДЗ №2: ≈20 год навчання на місяць, тобто ≈20 USD або 5 запусків; приймаємо його як місячний бюджет GPU. Ще одна оцінка: 40 merge у `main` на місяць, із них 4 стосуються моделі:

| Варіант | Запусків на місяць | Витрати на GPU | Висновок |
|---|---|---|---|
| Кожен merge у `main` | 40 | ≈162 USD | У 8 разів більше за бюджет |
| Лише вручну | за потреби | залежить від дисципліни | Дешево, але retraining затягується |
| Зміна config або коду + розклад раз на місяць (обрано) | 4 + 1 | ≈20 USD | Упритул до бюджету, запасу немає: кожен додатковий запуск — погодження AI PM |

Недолік обраного: зміна самих даних між плановими запусками навчання автоматично не запустить. Компенсація: запуск вручну на нову версію датасету, а коли моніторинг дозріє — сигнал drift.

## 5. Risk register

Шкала: Low / Medium / High. Ймовірність оцінено без заходів зі стовпця «Як зменшити ризик».

| Ризик | Ймовірність | Вплив | Як зменшити ризик | Owner |
|---|---|---|---|---|
| GitLab CI має надмірні AWS-права | Medium | High | OIDC і окремі ролі для dev, staging і prod: job запуску може лише стартувати `MLOpsPipeline`, job збірки — лише push в один репозиторій образів; умова на claim `sub` прив'язує ролі до проєкту й гілки `main`, захищеної в GitLab | MLOps Engineer |
| Постійні AWS-ключі в GitLab витекли через логи чи скопійовані налаштування | Medium | High | У production ключів немає, тимчасовий доступ через OIDC видається на один job і діє обмежений час. Для PoC — masked і protected змінні, ротація, дата переходу на OIDC | MLOps Engineer |
| Запуск на неякісних даних дає модель, якій не можна вірити | Medium | High | Обов'язковий data validation до навчання, зупинка за критичної помилки | Data Engineer |
| Модель навчилась, але гірша за production | Medium | High | Пороги, порівняння на тому самому наборі, manual approval | AI/ML Engineer + AI PM |
| Training запускається занадто часто | High | Medium | Правила запуску за змінами файлів і розклад (розд. 4) | AI PM |
| Неконтрольовані витрати на GPU | Medium | High | Timeout 6 год, погоджений тип інстансу, окремий бюджет в AWS Budgets із фільтром за `g5.xlarge`, алерти на 80 % (лишився приблизно один запуск) і 100 % (MLOps Engineer вимикає автоматичні trigger-и до кінця місяця, далі лише manual із погодженням AI PM). Дані Budgets оновлюються до трьох разів на добу, тож алерт приходить із запізненням | AI PM + MLOps Engineer |
| Pipeline впав, а реагувати нікому | Medium | High | Owner кожного етапу (розд. 2), сповіщення з owner-ом, ескалація до AI PM, якщо за один робочий день немає реакції | AI PM |
| Модель автоматично потрапила в production | Medium | High | Розділені навчання, реєстрація, approval і деплой; у workflow немає кроку, що виставляє approved або production, реліз — окремий PR у GitOps-репозиторії | Tech Lead |
| Run неможливо простежити: не передано commit або версію даних | Medium | Medium | Execution без Git-контексту зупиняється на першому кроці, run без контексту не реєструється | MLOps Engineer |

Перед використанням pipeline у production-сценарії мають працювати OIDC і окремі ролі, перевірка даних до навчання, автоматичні gates, заборона автопросування й обмеження витрат.

## 6. Acceptance criteria для Jira-задачі

**Задача:** «Інтегрувати GitLab CI з AWS Step Functions для automated training pipeline». Критерій вважається виконаним, лише якщо його можна перевірити у вказаному місці.

| ID | Критерій | Де перевірити |
|---|---|---|
| AC-01 | GitLab CI pipeline запускає AWS Step Functions workflow `MLOpsPipeline` | GitLab job log, AWS Console |
| AC-02 | В input execution передаються commit SHA, branch, `source="gitlab-ci"` і версія датасету | Input execution в AWS Console |
| AC-03 | Pipeline стартує лише за погодженими правилами: зміна config або коду, розклад, ручний запуск; merge, що не стосується моделі, навчання не запускає | Тестовий merge без змін моделі в GitLab |
| AC-04 | Execution і статус кожного кроку видно в AWS Console, логи — у CloudWatch | AWS Console, CloudWatch |
| AC-05 | Окремий крок data validation виконується до навчання, а за критичної помилки навчання не стартує | Тестовий запуск із битим датасетом |
| AC-06 | Метрики, параметри, артефакти, commit SHA і версія датасету записані в MLflow | MLflow run |
| AC-07 | Нова версія отримує статус candidate або rejected у Model Registry із посиланням на run | Model Registry |
| AC-08 | Команда отримує повідомлення про success і failure у форматі розд. 7 протягом 10 хв після завершення | Slack, тестові запуски обох видів |
| AC-09 | GitLab отримує доступ через OIDC: job запуску може лише стартувати цей workflow, job збірки — лише push в один репозиторій образів; для dev, staging і prod ролі окремі, секрети не потрапляють у логи | IAM-ролі, GitLab job log |
| AC-10 | Автоматичні quality gates (дані, ML-метрики, baseline, відтворюваність) перевіряються до зміни статусу: модель, гірша за production, отримує rejected | Тестовий запуск зі слабкою моделлю, Model Registry |
| AC-11 | Модель не переходить у production без approval: у workflow немає кроку, що виставляє approved або production, реліз іде лише через PR у GitOps-репозиторій | Опис workflow, захист гілки GitOps-репозиторію |
| AC-12 | Training job має timeout 6 год у workflow і в самому Job, погоджений тип інстансу і один повтор лише на збій ноди; бюджетні алерти налаштовано | Конфігурація workflow і Job, AWS Budgets |
| AC-13 | Є runbook: як перевірити статус, куди дивитися при помилці, хто реагує, як запустити повторно | README або runbook у репозиторії |

## 8. Короткий висновок

Automated training pipeline важливий для MLOps, бо замінює ручний запуск повторюваним процесом, у якому кожне навчання можна простежити від коміту до статусу моделі. GitLab CI відповідає за старт: визначає момент запуску, перевіряє код і передає Git-контекст. AWS Step Functions керує самим workflow: порядком кроків, повторами, timeout-ами й обробкою помилок, але модель не тренує. Технічний success означає лише, що кроки відпрацювали: модель може навчитися без жодної помилки й бути гіршою за поточну. Тому навіть успішний run завершується статусом candidate або rejected, а не релізом. Перед production-релізом потрібні проходження quality gates, порівняння з поточною моделлю, перевірка в staging, rollback-план і approval від ML Lead, AI PM та Tech Lead.
