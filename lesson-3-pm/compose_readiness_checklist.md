# Compose Readiness Checklist: локальний стенд ML-системи

Окремий контейнер із моделлю — ще не готова ML-система. Цей checklist оцінює, чи можна підняти весь локальний стенд однією командою. Стенд — наступний етап після образів (див. `ai_ml_team_task.md`), тому checklist підготовлено заздалегідь, а статуси — `TBD`, доки команда не надасть `compose.yaml`.

## Склад стенду

| Сервіс | Роль | Що підтверджує команда |
|---|---|---|
| `model-api` | HTTP API з endpoint `/health` і `/predict` | Образи `ml-infer-*` зараз розраховані на запуск через CLI; для стенду потрібен HTTP-режим. Окремий образ чи режим slim-образу — вирішує команда |
| model service / model runtime | Завантажує модель і виконує inference | Модель працює всередині `model-api` чи окремим сервісом; `model.pt` вшитий в образ чи монтується лише для читання |
| `redis` | Кеш або черга запитів | Роль на пілоті: кеш відповідей чи черга запитів |
| `postgres` | Журнал запитів і результатів inference | Схема й тестові дані лише локальні |
| `monitoring` | Локальний моніторинг: збір метрик сервісу (наприклад, Prometheus з endpoint `/metrics`) | Це не full monitoring: алерти, дашборди якості моделі й drift у production до стенду не входять |

## Checklist

| № | Перевірка | Очікуваний результат / як перевірити | Статус |
|---|---|---|---|
| 1 | Є `compose.yaml` | Файл у корені репозиторію; `docker compose config` виконується без помилок | TBD |
| 2 | Описаний `model-api` | Сервіс має `build` або `image`, порт, змінні середовища, health check | TBD |
| 3 | Описані всі залежні сервіси | `redis`, `postgres`, `monitoring` і model runtime (якщо він окремий) — у тому самому файлі; після запуску `docker compose ps` показує всі сервіси у стані running або healthy | TBD |
| 4 | Сервіси не потребують ручного запуску | Після однієї команди нічого не стартують вручну; у `redis` і `postgres` описаний `healthcheck`, а `model-api` чекає на їхню готовність (`depends_on` з умовою `service_healthy`) | TBD |
| 5 | Порт налаштований правильно | `model-api` доступний на погодженому порту, наприклад `8000:8000`; `curl http://localhost:8000/health` відповідає | TBD |
| 6 | Є health endpoint | `GET /health` повертає 200 лише тоді, коли модель завантажена, а не просто коли процес запущений | TBD |
| 7 | Є predict endpoint | `POST /predict` з тестовим зображенням повертає JSON за контрактом AC-07 | TBD |
| 8 | Конфігурації винесені в `.env` | `compose.yaml` не містить значень конфігурації (`MODEL_PATH`, адреси сервісів, рівень логів, облікові дані локальних БД) і лише посилається на файли змінних: `env_file` з `.env.example` (безпечні локальні значення, у git) і необов'язковим `.env` для перевизначень (`required: false`). Свіжий клон стартує без ручних кроків; `.env` — у `.gitignore` | TBD |
| 9 | Немає production-секретів | У `compose.yaml` і `.env.example` лише локальні тестові значення; у CI працює сканер секретів (наприклад, gitleaks) | TBD |
| 10 | Стенд не підключений до production DB, Redis або queue | Адреси БД, кешу й черги — імена сервісів Compose (`postgres`, `redis`), а не production-хости; production-адрес немає ні в `compose.yaml`, ні в `.env.example` | TBD |
| 11 | Команда `docker compose up --build` описана в README | README містить команду запуску й перевірки `/health` і `/predict` | TBD |

## Висновок

Локальний стенд можна вважати готовим, якщо всі сервіси піднімаються однією командою, а test prediction виконується без ручних дій.

Оцінка на поточний стан: стенд ще не готовий. `compose.yaml` не надано, перевірено 0 пунктів з 11, а HTTP-режим `model-api` поки лише припущення, яке має підтвердити команда. Висновок зміниться, коли пункти 1–11 матимуть статус «так». Від цього висновку залежить рішення про перехід до staging (`optimization_report_review.md`).
