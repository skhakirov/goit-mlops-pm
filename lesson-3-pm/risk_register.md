# Risk Register: контейнеризація моделі класифікації зображень

Ризики delivery на поточному етапі: команда готує образи `ml-infer-fat:1.0` і `ml-infer-slim:1.0`, а локальний стенд Docker Compose іде наступним етапом. Ймовірність оцінена для стану до здачі артефактів і переглядається після отримання `report.md`.

| ID | Ризик | Ймовірність | Вплив | Mitigation | Owner |
|---|---|---|---|---|---|
| R-01 | Image працює локально, але не готовий до staging | Medium | High: проблеми виявляються вже на staging, реліз зсувається | Виконання AC-01…AC-15 і всіх 20 пунктів `docker_image_review.md`; збірка обох образів у CI; на staging — лише образ із registry, а не локальна збірка | AI PM |
| R-02 | Slim image дає інший prediction, ніж fat | Medium | High: користувачі отримують інші класи, ніж у перевіреній версії, і дефект непомітний | Порівняння fat і slim на однаковому test input — умова приймання slim (AC-08); при розбіжності slim не приймається, еталоном лишається fat | AI/ML Engineer |
| R-03 | Несумісність версій Python, torch або torchvision | Medium | High: образ не збирається або модель не завантажується; формат `model.pt` може не підійти до нової версії torch | Версії через `==` (AC-13); письмове підтвердження сумісності з Python 3.13; збірка обох образів у CI на кожну зміну `requirements.txt` | AI/ML Engineer |
| R-04 | Зайві файли потрапляють у build context | High | Medium: більший образ, повільніша збірка, ризик витоку `.env` або даних | `.dockerignore` (AC-12); перевірка вмісту slim-образу (AC-11) | DevOps |
| R-05 | Немає README з командами | Medium | Medium: результат не може відтворити ніхто, крім автора | Команди build і run у README (AC-09); QA відтворює збірку й запуск на чистій машині до закриття задачі | QA |
| R-06 | Немає порівняння fat і slim | Medium | Medium: оптимізацію неможливо виміряти, і рішення про staging ухвалюється навмання | `report.md` — обов'язковий deliverable (AC-10); без нього задача не закривається | AI PM |
| R-07 | Production-секрети потрапили в Compose | Medium | High: інцидент безпеки і витік облікових даних у репозиторій | `.env` поза git, у репозиторії лише `.env.example` з тестовими значеннями; сканер секретів у CI; негайна ротація в разі витоку | DevOps |
| R-08 | Локальний стенд підключається до production DB або queue | Low | High: тестові запити змінюють або псують production-дані | У конфігурації лише імена сервісів Compose; production-адрес немає в репозиторії; локальні облікові записи без доступу до production | DevOps |
| R-09 | Немає версії model artifact | Medium | High: неможливо пояснити, яка модель дала prediction, і неможливо відкотитися | `model_version` у відповіді; джерело моделі й sha256 `model.pt` у README (AC-15) | AI/ML Engineer |
| R-10 | Image завеликий для швидкого delivery | High | Medium: повільний pull на staging, довший цикл hotfix, витрати на сховище | CPU-збірка torch в обох образах (AC-14); multi-stage для slim (AC-03); ліміт розміру погоджується після першого вимірювання | AI/ML Engineer |

Ризики R-02 і R-09 блокують приймання slim-образу незалежно від інших результатів: без збігу inference і без версії моделі оптимізація не приймається.
