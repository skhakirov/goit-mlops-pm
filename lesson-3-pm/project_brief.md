# Project Brief: контейнеризація моделі класифікації зображень

## 1. Бізнесовий контекст

Компанія запускає пілот автоматичної попередньої класифікації фото товарів для внутрішнього каталогу. Менеджер завантажує зображення, сервіс пропонує три найімовірніші класи — що саме зображено на фото, — а людина підтверджує або виправляє вибір.

На цьому етапі модель повертає стандартні класи ImageNet без донавчання. Зіставлення цих класів із категоріями каталогу — окрема задача наступного етапу.

Мета цього етапу — не покращити модель, а отримати керований delivery-артефакт: модель, яку однаково запускають на ноутбуці інженера, у CI/CD і на staging.

## 2. Яку модель контейнеризуємо

- Пропозиція PM, яку підтверджує команда: pretrained-модель ResNet-18 з `torchvision.models`, ваги `ResNet18_Weights.IMAGENET1K_V1` (1000 класів ImageNet).
- Артефакт моделі — `model/model.pt`. Формат файлу (state_dict, TorchScript чи повна модель через `torch.save(model)`) підтверджує AI/ML Engineer.
- Версія моделі для відповідей і логів (пропозиція): `model_version = resnet18-imagenet1k-v1`. Це не те саме, що тег образу `1.0`: тег описує збірку, `model_version` — модель усередині неї.

## 3. Для чого потрібен inference

Inference — це запуск уже навченої моделі на новому зображенні: на вхід подається файл зображення, на виході — три найімовірніші класи з confidence. Саме inference і є продуктовою функцією пілоту. Тренування моделі на цьому етапі немає.

## 4. Чому Docker image — delivery-артефакт

`ML-модель + inference-код + залежності + системне середовище = Docker image`.

Далі передається саме image, а не «папка з кодом»: локальна збірка → registry → CI/CD → staging → production. Версії Python і бібліотек зафіксовані всередині образу, тому зникає клас проблем «працює тільки на моєму ноутбуці».

## 5. Чому очікуються два варіанти образу

| Образ | База | Навіщо |
|---|---|---|
| `ml-infer-fat:1.0` | `python:3.13` | Простий образ для першої перевірки, що модель запускається в контейнері. Еталон поведінки моделі. |
| `ml-infer-slim:1.0` | `python:3.13-slim`, multi-stage build | Оптимізований образ: у фінальний образ потрапляють лише runtime-залежності, модель і inference-код. Менший розмір, швидший pull, менша attack surface. |

Пара «fat → slim» робить оптимізацію вимірюваною: є стан «до» і стан «після».

## 6. Головна умова оптимізації

Оптимізація не повинна змінювати поведінку моделі. На однаковому тестовому зображенні slim повертає ті самі top-3 класи в тому самому порядку, що й fat, а confidence на кожній позиції відрізняється не більше ніж на 0.001.

Спершу перевіряємо коректність inference, і лише потім — розмір, швидкість і безпеку.

## 7. Технічні рамки

Нижче — припущення PM, які команда підтверджує або виправляє до початку роботи:

- inference виконується на CPU, GPU runtime не потрібен; torch і torchvision в обох образах — CPU-збірки з одного `requirements.txt`;
- запуск — через CLI: `docker run` з тестовим зображенням, змонтованим із хоста лише для читання;
- відповідь — JSON за контрактом з `acceptance_criteria.md` (AC-07);
- якщо команда використовує скрипт підготовки середовища, він ідемпотентний, не містить секретів і описаний у README.

## 8. Де результат має бути придатний для перевірки

| Середовище | Що має працювати | Хто перевіряє |
|---|---|---|
| Локально | Збірка й запуск обох образів за командами з README | AI/ML Engineer, потім QA на чистій машині |
| CI/CD | Автоматична збірка обох образів і тестовий inference з порівнянням fat і slim | DevOps |
| Staging | Slim-образ із registry запускається без ручних дій. Умова переходу: виконані AC, `report.md`, розглянутий security scan і готовий локальний стенд Docker Compose (окремий етап) | DevOps і QA; рішення про перехід ухвалює AI PM |

Production-розгортання до цього етапу не входить.
